### 0.1 Hard rules (breaking any of these invalidates the result)
- R1. Scoring code sees only query text and document text. It never reads qrels, query or document IDs, or any `meta_information` field. IDs may be used only as dictionary keys to return results, never as features. A unit test must shuffle all IDs and assert the ranking of texts is unchanged.
- R2. No tuning on the test split. All selection uses the validation split carved from train (Section 10.1). The test split is run only for frozen configs, and every test run is logged.
- R3. Test qrels are loaded only inside the final MTEB evaluation. No script in this repo opens them for analysis or debugging.
- R4. Untrusted code (every APPS document) runs only inside the sandbox in Section 11.3. Never `exec`, `eval` or `import` a document in the main process.
- R5. The submitted pipeline must run on CPU. GPUs may speed up development encodes; the README defaults to `device: cpu`, and a CPU spot-check must reproduce GPU embeddings (Section 6).

## 1. Goal and honest targets

- Target: the highest clean NDCG@10 and MRR on MTEB `AppsRetrieval` (screening), plus P1 and a small Bonus for hands-on.
- The user's aspiration is >95% on every metric. The council's position: this is unlikely to be reachable without leakage, and nothing in this plan guarantees it. Each query has exactly one relevant document [V: CoIR paper], so 0.95 NDCG@10 means ranking the gold solution first on roughly 87-95% of queries.
- Reference points (NDCG@10 x100 on APPS): E5-base-v2 11.5, BGE-base 6.5, Granite-R2 14.0, gte-modernbert-base 56.4 [V: Granite R2 paper Table 11; EmbeddingGemma paper]. CodeXEmbed 0.48, 0.62 with 22-30B LLM rewriting [V snippet: arXiv 2605.08299].
- Strategy in one line: an embedder gets the gold solution into the top-k (recall); an execution check on the statement's sample I/O picks it out (precision at rank 1).
- Success is measured, not assumed: Gate G2 (Section 9) computes the achievable ceiling on validation before any tuning.

## 4. Facts about the data

- `CoIR-Retrieval/apps`: corpus 8.77k, queries 8.77k, qrels train 5k / test 3.77k [V: HF]. The test corpus contains all 8,765 documents, train solutions included as distractors [V3; VERIFY in Phase 0].
- The same corpus serves validation and test, so the corpus is encoded once per config and cached.
- Python only. Query = full contest statement (~1.4K words); document = one whole solution script (~575 words) [V: CoIR paper Table 2]. Documents are top-level scripts, often with obfuscated names [V: Table 8].
- Statements usually contain sample input/output. Some APPS problems are call-based (starter code such as `class Solution`), not stdin/stdout [H: measure the share]. Some solutions may be Python 2 [H: measure].
- A paper reports severe duplication in Apps [V: arXiv 2505.12697]; near-duplicate problems can have solutions that also pass each other's samples.
- MTEB JSON reports fractions (0-1); papers report x100.

## 5. Architecture

```
                     ┌─────────────────── Stage 1 (recall) ───────────────────┐
query text ─► QueryPre ─►│ Embedder A (bake-off winner)  ─┐                         │
                         │ [optional Embedder B] ─────────┼─► weighted concat ─► L2 │─► cosine over corpus
doc text ───► DocPre ───►│   (same models, doc side)     ─┘                         │     └─► top-k
                     └───────────── EmbeddingCache: key = sha1(model|config|text) ─┘

                     ┌────────────────── Stage 2 (precision) ──────────────────┐
top-k (query, doc) ─►│ SampleIO parser (from query text) ─► Sandbox runner      │
                     │ outcome ∈ {PASS, WRONG, ERROR, TIMEOUT, UNKNOWN}           │
                     │ score = cos + w_pass·PASS − w_wrong·WRONG − w_err·ERROR    │
                     │ ties → cosine;  ExecCache: key = sha1(doc)|sha1(input)     │
                     └────────────────────────────────────────────────────────────┘

Output A (always, guideline-compliant): mteb.evaluate(PrePostPipelineEncoder) → results/appsretrieval_results_A.json
Output B (if G2, G3, G4 pass): MTEB two-stage: Stage-1 predictions → ExecutionReranker → results/appsretrieval_results_B.json
Path B (hands-on): versioned index over git/snapshot/JSONL sources, reusing Stage 1 (+ optional --verify Stage 2)
```

Why fusion is valid inside `AbsEncoder`: if u1, u2 are unit vectors from two models and v = [√w·u1, √(1−w)·u2], then ‖v‖ = 1 and cos(v_q, v_d) = w·cos1 + (1−w)·cos2. A hybrid score, computed by MTEB's own cosine.

### 10.4 Encoder skeleton (VERIFY every API detail)
```python
# src/codeintel/stage1/encoder.py
import numpy as np
from mteb.models.abs_encoder import AbsEncoder
from mteb.models.model_meta import ModelMeta
from mteb.types import PromptType

class PrePostPipelineEncoder(AbsEncoder):
    def __init__(self, cfg_path="configs/stage1_final.yaml"):
        self.cfg = load_cfg(cfg_path)
        self.models = [load_model(m, device=self.cfg.device) for m in self.cfg.models]  # 1 or 2 models
        self.weights = self.cfg.fusion_weights                                        # e.g. [1.0] or [0.7, 0.3]
        self.query_pre, self.doc_pre = build_query_pre(self.cfg), build_doc_pre(self.cfg)
        self.cache = EmbeddingCache(self.cfg.cache_dir)   # key = sha1(model_id|config fingerprint|preprocessed text)
        self.mteb_model_meta = ModelMeta.create_empty(overwrites=dict(
            name="<team>/apps-code-retriever", revision="1"))                          # VERIFY required fields

    def encode(self, inputs, *, task_metadata, hf_split, hf_subset,
               prompt_type: PromptType | None = None, **kwargs):
        texts = [t for batch in inputs for t in batch["text"]]                        # VERIFY batch schema
        is_query = prompt_type == PromptType.query
        texts = [self.query_pre(t) if is_query else self.doc_pre(t) for t in texts]
        parts = [np.sqrt(w) * l2(self.cache.get_or_compute(m, texts, is_query))
                 for m, w in zip(self.models, self.weights)]
        return l2(np.concatenate(parts, axis=1)).astype(np.float32)
```
Unit tests: output shape, unit norm, fusion identity (cosine of concatenation equals weighted cosines within 1e-5), and R1 ID-shuffle invariance.

## 11. Stage 2 details: execution-verified reranking

### 11.1 Sample I/O parser (`sampleio.py`)
- Inspect 50 validation statements first and log the marker styles that occur. Expected styles [H]: `-----Example-----`, `-----Examples-----`, `Sample Input` / `Sample Output` (numbered or not), `Example 1:` blocks, `Input` / `Output` headings followed by example blocks. Do not confuse the input *specification* (`-----Input-----` describing the format) with example data.
- Return a list of (input, expected_output) pairs; empty list = UNKNOWN (no samples).
- Detect call-based problems (starter code, `class Solution`, function signatures without stdin) and mark them UNKNOWN in v1 [H: measure the share; a call-harness is a stretch goal only if the share is large].

### 11.2 Output comparison (`compare.py`)
Token-wise after `split()`: exact tokens match; else numeric tokens within 1e-6 relative/absolute; optional case-insensitive mode for YES/NO style answers (enable only if it raises the gold PASS rate on validation). Lengths must match. PASS requires every sample to pass.

### 11.3 Sandbox (`sandbox.py`)
Default: one long-lived Docker container from `Dockerfile.sandbox` (`python:3.11-slim`, plus `python2` if cheaply available), started with `--network none --memory 4g --pids-limit 512 --read-only --tmpfs /tmp:rw,size=256m --cap-drop ALL --security-opt no-new-privileges`, non-root user. The worker pool inside runs each program with:
```python
subprocess.run([PY, "-I", prog_path], input=sample_in, capture_output=True,
               timeout=T_WALL, cwd=tmpdir, env={"PATH": "/usr/bin:/bin"},
               preexec_fn=set_limits)     # RLIMIT_CPU, RLIMIT_AS (512 MB), RLIMIT_FSIZE (1 MB), RLIMIT_NPROC (in container only)
```
- Truncate stdout at 1 MB. Kill the process group on timeout. Delete the temp dir after each run.
- Python 2: if `compile()` raises `SyntaxError` under Python 3, run with `python2` if present; otherwise UNKNOWN.
- Defaults [H]: T_WALL = 2 s per sample; tune only if the gold TIMEOUT rate on validation is high.
- Fallback without Docker (Linux only): `unshare -rn` + the same rlimits; never run unsandboxed. Log which mode ran.
- Parallelism: a process pool sized to physical cores; results cached in `cache/exec/` keyed by sha1(doc text) + sha1(sample input) + sandbox version.

### 11.4 Outcomes and score
Outcome ∈ {PASS, WRONG (ran, output differs), ERROR (exception / nonzero exit), TIMEOUT, UNKNOWN}.
`score = cosine + w_pass·[PASS] − w_wrong·[WRONG] − w_err·[ERROR]`; TIMEOUT and UNKNOWN add nothing. Ties break by cosine. Cosine comes from the Stage 1 cache (text-keyed, so R1 holds).

### 11.5 Tuning (validation only, tiny grid to limit overfitting)
k ∈ {10, 20, 50}; w_pass ∈ {0.1, 0.3, 1.0}; w_wrong ∈ {0, 0.05, 0.1}; w_err ∈ {0, 0.05}. 54 configs, all re-scored from cached executions (no re-running code). Choose by validation NDCG@10; report MRR too; confirm with G3. Log the full grid.

### 11.6 MTEB integration for Output B (VERIFY against installed mteb and the two-stage docs)
- Run Output A with `prediction_folder="results/predictions/stage1"` so first-stage rankings are saved.
- Implement `ExecutionReranker` following mteb's cross-encoder protocol: it receives (query text, document text) pairs and returns one score per pair = Section 11.4 score. It computes cosine from the Stage 1 cache and executes through the sandbox pool, batching all pairs of a call in parallel.

## 12. Path B details: P1 and Bonus

### 12.1 Inputs and units
- Sources: git repo (listed revisions, first-parent), snapshot directories, or JSONL files (`{"id","text","path"?}` per line), one per version.
- Unit = one file or one JSONL snippet. Files longer than the document token cap split into ~80-line windows (20 overlap) sharing the unit id; results collapse back to units.
- Embedding text = Stage 1 frozen config. Optional `--verify` runs Stage 2 on the top-k when the query contains parseable sample I/O.

### 12.2 Store (`index.sqlite` + `vectors.npy`)
```sql
CREATE TABLE versions(version_id INTEGER PRIMARY KEY, ordinal INTEGER UNIQUE, label TEXT, source_ref TEXT);
CREATE TABLE units(unit_id INTEGER PRIMARY KEY, first_version INTEGER, last_version INTEGER);
CREATE TABLE revisions(rev_id INTEGER PRIMARY KEY, unit_id INTEGER, path TEXT, start_line INTEGER,
                       end_line INTEGER, emb_key TEXT, v_from INTEGER, v_to INTEGER);  -- NULL v_to = alive
CREATE TABLE embeddings(emb_key TEXT PRIMARY KEY, row INTEGER);
-- indexes: revisions(unit_id), revisions(emb_key), revisions(v_from, v_to)
```
`emb_key` = the Stage 1 cache key, so identical content across versions, files or renames maps to one vector. Search = masked brute-force dot product in numpy [H: fast enough at this scale].

### 12.3 Incremental update (P1)
1. Changed units: `git diff --name-status -M <prev> <new>`; file hashes for snapshots; id + text hash for JSONL.
2. Recompute `emb_key` only for changed units; embed only missing keys.
3. Close vanished revisions (`v_to = new − 1`), open new ones.
4. Log per-step times and the same update as a full rebuild. Headline P1 numbers: incremental vs full time, % embeddings reused.

### 12.4 Unit identity and search
- `unit_id` persists by same path (git rename detection carries it) or same JSONL id; otherwise identical `emb_key` (moved unchanged); else new.
- `search --rev R "query"` (P1): revisions alive at R, collapse windows, top-k.
- `search --range A..B "query"` (Bonus): all revisions alive in the range, collapse by `unit_id`, one result per unit with its best revision (ties → most recent), versions matched, and history (introduced / modified / unchanged / removed from `emb_key` changes). Keep per-revision scores in output.
- Output per result: rank, unit id, path, lines, snippet, score, version info; response carries encode/search/verify timings in ms.

### 12.5 Simulator and evaluation
`simulate_versions.py` builds 5 versions of a validation mini-corpus (validation gold docs + 1,500 distractors, train split only): whitespace/comment edits, variable renames, small code edits, additions and deletions, with ground-truth unit ids. Report on validation queries: single-version NDCG@10/MRR@10; all-versions without vs with collapse (unit-level); incremental vs full rebuild time; embeddings reused (%). Also demo P1 on a small real git repo over 3-4 commits.

## 17. Risks and fallbacks
| Risk | Mitigation |
|------|------------|
| Stage 2 disallowed for screening | Output A always produced; Stage 2 shown in hands-on |
| mteb two-stage API differs | Phase 0 verification; deadline Tue 18:00 for B, else fallback |
| Gold PASS rate low (parser, py2, call-based) | Measured in Phase 2a; fix top failure causes; UNKNOWN is neutral, so Stage 2 cannot hurt those queries much |
| Near-duplicate problems pass each other's samples | Ties break by cosine; report the duplicate-pass rate |
| Sandbox escape or machine damage | Docker with no network, read-only FS, rlimits, non-root; hostile-program tests in Phase 2a |
| Qwen3-0.6B too slow on CPU | Throughput measured in bake-off; drop it if the full CPU run is impractical |
| Kaggle/Colab session loss | Caches written to persistent storage after each chunk; encode script resumable |
| Overfitting validation | Tiny grids, bootstrap gate, single test run per frozen config |
| Val→test shift (difficulty mix) | Report both; do not re-tune on test |
| Time overrun | Ship the last completed phase; Output A from Phase 0 is the floor |
